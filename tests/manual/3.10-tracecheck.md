# Manual smoke: Tempo service map (stage 3.10)

This runbook walks one operator through a single end-to-end check that
proves the W3C `traceparent` header is propagated through `order` →
Kafka → `payment` → Kafka → `inventory`, that all three spans land in
Tempo under one `trace_id`, and that the Tempo Service Map draws the
matching edges.

It is **manual** — there is no automated assertion. The check is the
last gate of stage 3.10 (sub-task 3.10.f) and is intentionally cheap
to repeat on a fresh checkout.

## Prerequisites

- Docker (for `docker compose`) and GNU Make (for `make run-*`).
- `curl` and a browser. No test framework is invoked.
- The four orderflow binaries build cleanly (`make build`) — the runbook
  does not exercise compilation, only runtime behaviour.
- An `examples/order.json` file with a valid order payload — see step 3
  below for the shape; if missing, the file can be created from the
  `submitRequest` struct in `services/order/internal/api/handler.go`.

## What you'll verify

1. Each running service emits OTLP gRPC spans to `otel-collector:4317`.
2. The collector forwards them on to Tempo.
3. A single `POST /v1/orders` produces a trace whose spans are owned by
   three different services under one `trace_id`.
4. Tempo's Service Map view shows the edges
   `order → payment` and `payment → inventory`.

## Steps

### 1. Bring up the data + observability stack

```bash
docker compose -f deploy/docker-compose.yml up -d
```

Wait until `tempo`, `otel-collector`, `prometheus`, `grafana` and
`postgres-{order,payment,inventory}` all report healthy:

```bash
docker compose -f deploy/docker-compose.yml ps
```

Smoke that Grafana is reachable: open `http://localhost:3000`
(login `admin` / `admin`).

### 2. Start the four services in separate terminals

Each command honours the platform env vars
`OTEL_EXPORTER=otlp` (set as a default by the service's
`envOrDefault` block) and
`OTEL_EXPORTER_OTLP_ENDPOINT=otel-collector:4317`
(also defaulted by the service). You should **not** need to export
them manually — the defaults exist for this exact reason.

Open four terminals side by side and run one command per terminal:

```bash
# terminal A
make run-order

# terminal B
make run-payment

# terminal C
make run-inventory

# terminal D
make run-saga
```

Each process should print a line like
`orderflow-order starting version=0.0.0-dev table=order_outbox`.
If `InitTracing` fails to dial `otel-collector:4317`, the gRPC
exporter will keep retrying in the background — the binary still
serves HTTP traffic; only traces are dropped. (If you see that, the
collector container is not on the same Docker network as the binary;
restart with `docker compose up -d`.)

### 3. Make one end-to-end request

The order service binary wires `POST /v1/orders` once stage 3.11
lands; until then this command will return a 404, but the
trace-context plumbing (chi HTTP middleware → outbox envelope →
Kafka → consumer span) is in place from stage 3.10 — every HTTP
request the binary *does* serve (currently `/healthz`, `/metrics`)
already carries a `traceparent`, so you can still observe a
service-side span in Tempo via the fallback below.

```bash
curl -X POST localhost:8081/v1/orders \
     -H 'content-type: application/json' \
     -d @examples/order.json
```

If `examples/order.json` does not yet exist, create one in the
shape the `submitRequest` struct expects:

```json
{
  "customer_id": "11111111-1111-1111-1111-111111111111",
  "items": [
    { "sku": "BOOK-001", "quantity": 1, "unit_price_cents": 1999 }
  ]
}
```

**Fallback while `/v1/orders` is unimplemented:** `curl` any of the
already-mounted endpoints to still see a single-service span in
Tempo:

```bash
curl -i localhost:8081/healthz   # order
curl -i localhost:8082/healthz   # payment
curl -i localhost:8083/healthz   # inventory
curl -i localhost:8084/healthz   # saga
```

Each of these is wrapped by the chi middleware stack and produces
one HTTP-server span per request, which is enough to verify the
collector → Tempo path end-to-end while you're waiting on `/v1/orders`.

### 4. Open Tempo in Grafana and pick a trace

1. Open `http://localhost:3000/explore`.
2. Pick the **Tempo** data source from the dropdown.
3. Use the **Search** tab.
4. Filter by **Service Name** = `order_outbox` (the `TableName` the
   order service uses as its `service.name` resource attribute; the
   other services will appear as `payment_outbox`,
   `inventory_outbox`, `saga_outbox`).
5. Click the most recent trace — you should see a waterfall with one
   HTTP-server span at the root plus downstream spans for the kafka
   publish, consumer receive, and any HTTP route in the path.

   For the **Service Map** view: switch the Explore query type from
   **Search** to **Service Graph**; Tempo will draw a node per
   `service.name` and an edge for every observed parent → child span
   pair. The expected first edges are:

   ```
   order_outbox ──▶ payment_outbox
   payment_outbox ──▶ inventory_outbox
   ```

   (Spans for the saga service are produced out of band — its HTTP
   surface is wired but the orchestrator itself runs in a later
   stage, so saga edges may be absent until that lands.)

### 5. Save the evidence

Take a screenshot of the Tempo Service Graph and drop it at:

```
docs/demo/screenshots/tempo-service-map.png
```

This file is the durable, human-visible artefact of stage 3.10.
Subsequent stages can replace it as the service map grows.

## Checklist

Copy this block into the PR description or commit body and tick each
box after you have personally observed the corresponding outcome.

- [ ] `docker compose -f deploy/docker-compose.yml ps` shows all
      services healthy.
- [ ] `make run-order`, `make run-payment`, `make run-inventory`,
      `make run-saga` each log a `starting` line.
- [ ] At least one HTTP request has been made against the running
      order service (either `/v1/orders` if stage 3.11 has landed or
      `/healthz` as the fallback).
- [ ] Grafana → Explore → Tempo shows a trace for
      `service.name=order_outbox` within the last minute.
- [ ] The trace contains spans owned by **all three** of
      `order_outbox`, `payment_outbox`, `inventory_outbox` under one
      `trace_id`.
- [ ] The Tempo Service Graph shows the edges
      `order_outbox → payment_outbox` and
      `payment_outbox → inventory_outbox`.
- [ ] `docs/demo/screenshots/tempo-service-map.png` is committed.

## Cleanup

When you're done:

```bash
# stop the four binaries: Ctrl-C in each terminal
docker compose -f deploy/docker-compose.yml down
```

Tempo's local volume is ephemeral in the shipped
`deploy/docker-compose.yml`, so traces go away with the container —
that is intentional for this smoke test.

## What this runbook does not prove

- It does **not** assert that propagation works under high load —
  that is the job of `tests/load/3.x-trace-throughput.md` (or
  whatever sub-stage lands that test).
- It does **not** assert that the collector survives a process
  restart — the brief is verifying the happy path. The
  chaos suite under `tests/chaos/` is where restarts and dropped
  packets are exercised.
- It does **not** trigger an automated assertion. A human must look
  at the Tempo UI and tick the boxes; this is deliberate so the
  smoke check costs zero CI minutes.
